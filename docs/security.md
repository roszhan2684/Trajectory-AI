# Security & threat model

Scope: the system as implemented in this repository (demo identity, JSON-persisted store, local adapters). Each threat lists the control in code and the residual risk.

| #   | Threat                                                                       | Controls (where)                                                                                                                                                                                                                                                                                                                                              | Residual risk                                                                                                                      |
| --- | ---------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| 1   | **Cross-tenant data access** by changing IDs in URLs or API calls            | Every org-owned read/write goes through `assertTenant()` (`services/core.ts`) and returns **404**, not 403, for other tenants' objects. Candidate global profiles are shared by design; org-specific matches/conversations/intros are filtered by `organizationId`. Covered by `tests/services.test.ts` and the Playwright tenant test.                       | A service that forgets `assertTenant` would leak; mitigated by tests per entry point and keeping data access inside services only. |
| 2   | **Privilege escalation** (viewer refines ranking, recruiter invites members) | Capability matrix (`engine/policy/rbac.ts`) enforced with `requireCap()` in services; UI hiding is cosmetic only. OWNER/INTERNAL_OPERATOR can't be granted by invite or role change.                                                                                                                                                                          | Hiring-manager intro approval is an org setting — misconfiguration is possible but audited.                                        |
| 3   | **Session forgery / theft**                                                  | HMAC-SHA256 signed cookie, `HttpOnly`, `SameSite=Lax`, `Secure` in production, 14-day expiry, timing-safe compare (`auth/tokens.ts`). Production refuses to start signing without `SESSION_SECRET` (≥32 chars).                                                                                                                                               | Demo sign-in has no password by design (persona picker). Supabase Auth would replace it.                                           |
| 4   | **Candidate portal link guessing / tampering**                               | Portal URLs carry a signed, expiring token bound to one conversation; the stored token must also match. Opportunity pages verify the match belongs to that conversation. Tampered tokens → "invalid or expired" (tested).                                                                                                                                     | Anyone holding a valid link can act as that candidate until expiry (30 days) — same as email magic links.                          |
| 5   | **Prompt injection via resumes or briefs**                                   | No LLM executes anything. Parsing is deterministic and tool-less; instruction-like text is detected (`nlp/safety.ts`), flagged to humans and stripped from normalized role text. Source text is rendered as text, never HTML.                                                                                                                                 | A future LLM layer must keep these boundaries (see `ai-safety.md`).                                                                |
| 6   | **Document abuse** (huge/malformed/non-PDF uploads)                          | 5 MB limit, MIME + `%PDF-` magic-byte check, text extraction server-side via `unpdf`, minimum text length, checksum dedupe, ingestion runs as a bounded job with permanent-error classification.                                                                                                                                                              | PDF parser vulnerabilities are inherited from `unpdf`/pdf.js; keep dependencies patched.                                           |
| 7   | **SSRF / path traversal**                                                    | No user-supplied URLs are fetched. GitHub import is a deterministic synthetic adapter that validates the handle (`^[a-z0-9-]{1,39}$`). The data dir is fixed by env, never by request input.                                                                                                                                                                  | A real GitHub adapter must allow-list `api.github.com`.                                                                            |
| 8   | **Secret exposure**                                                          | Secrets read only in server modules (`server-only` on session/http). `.env.example` has no values. API keys are stored as SHA-256 hashes and shown once. Errors are mapped to user-safe messages (`http.ts toError`), details logged server-side only.                                                                                                        | Seeded `trj_demo_*` keys are public by design for local MCP demos — **not production auth**.                                       |
| 9   | **Unauthorized side effects** (intros sent, rankings changed by an agent)    | Intro state machine rejects invalid transitions; sending requires candidate consent + recruiter approval; "sent" is an internal record. Feedback only creates proposals; applying is a separate, audited, reversible step. MCP write tools create drafts or require `confirm=true`. Jobs are idempotent (replays dedupe; matches upsert by role × candidate). | An MCP client with a recruiter's key can apply a refinement after `confirm=true` — that's the intended human-in-the-loop contract. |
| 10  | **Search-index leakage**                                                     | No browser search key exists; all search runs server-side behind `candidates.search`. Index documents contain no contact details or raw resume beyond the profile text.                                                                                                                                                                                       | A Typesense deployment must use scoped search-only keys if browser search is added.                                                |
| 11  | **Telemetry/PII leakage**                                                    | `track()` keeps only short scalar properties (free text dropped — tested); traces carry hashed org IDs and no candidate text.                                                                                                                                                                                                                                 | Candidate names appear in audit metadata only by ID.                                                                               |
| 12  | **Abuse / cost** (expensive endpoints)                                       | In-memory token buckets on parse, ingest, matching, refinement, eval, search, portal answers, demo reset.                                                                                                                                                                                                                                                     | Per-instance only; use Redis/Upstash in multi-instance deployments.                                                                |
| 13  | **XSS / clickjacking**                                                       | React escaping everywhere (no `dangerouslySetInnerHTML` except the static theme script); CSP (`default-src 'self'`, `frame-ancestors 'none'`), `X-Frame-Options: DENY`, `nosniff`, strict referrer policy (`next.config.ts`).                                                                                                                                 | CSP allows `'unsafe-inline'` scripts/styles (Next.js runtime + theme script); a nonce-based CSP would tighten this.                |
| 14  | **CSRF**                                                                     | Mutations are Next.js server actions (origin-checked by the framework) or JSON APIs requiring a bearer key or same-site cookie.                                                                                                                                                                                                                               | —                                                                                                                                  |
| 15  | **Destructive data operations**                                              | `pnpm seed:reset` refuses `NODE_ENV/VERCEL_ENV=production`; UI demo reset is owner-only and disabled on production unless explicitly allowed. Candidate deletion is owner/admin-only and audited.                                                                                                                                                             | —                                                                                                                                  |

## MCP authorization

Local: per-user API key (`Authorization: Bearer`), hashed at rest, scoped to one organization, revocable, `lastUsedAt` tracked. Production: replace with OAuth 2.1 per the MCP authorization spec (authorization-code + PKCE, short-lived tokens with org + capability scopes), keeping the same server-side `requireCap` checks.

## Dependency hygiene

`pnpm audit` in CI is recommended; Dependabot/Renovate optional. Build scripts are allow-listed (`pnpm-workspace.yaml → allowBuilds`).
